# 企业知识库 · 技术选型脑暴

> 目标：用最主流、最不容易被淘汰的技术栈，搭一套企业级知识库（Enterprise Knowledge Base）。
> 定位：内部文档问答 + 权限感知检索 + 引用溯源 + 增量索引。

---

## 0. 先定一个决定全局的前提

在写任何代码之前，必须先回答：**"自建"还是"用开源平台改"？**

| 路线 | 代表 | 适合 | 不适合 | 起步速度 |
|---|---|---|---|---|
| **A. 开箱即用** | Dify / RAGFlow / MaxKB / FastGPT | 3 个月内要上线、团队没有 AI 工程能力、文档格式单一 | 深度定制检索逻辑、复杂权限模型、需要多租户 SaaS 化 | 天级 |
| **B. 深度二开** | RAGFlow / Dify 源码级改造 | 需要文档深度解析能力（表格/扫描件）但不想自己造解析器 | 团队要掌控全部链路 | 周级 |
| **C. 全自建** | LangGraph + 自研编排 | 检索策略要持续演进、要沉淀自有资产、规模大 | 时间紧、文档解析这块要重复造轮子 | 月级 |

**我的建议：C 为终态，B 为起点。**
不要一上来全自建 —— 文档解析（PDF 表格、扫描件、多栏排版）是这个领域**最难且最被低估**的部分，自己踩坑要 2-3 个月。而 RAGFlow 的深度文档解析是目前开源里最成熟的一档。

具体做法：**先以 RAGFlow/Dify 为底座跑通检索效果基线，验证完"检索质量能不能打"之后，再决定哪些模块值得剥离自建。** 这样既不重复造轮子，又不会把自己锁死在别人的抽象里。

## 1. 整体分层架构

```
┌─────────────────────────────────────────────────────┐
│ 应用层    Web对话台 / OpenAPI / 钉钉·飞书机器人 / 权限中心 │
├─────────────────────────────────────────────────────┤
│ 生成层    LiteLLM网关 → DeepSeek-V4.1-Flash/Qwen3 → 引用溯源 │
├─────────────────────────────────────────────────────┤
│ 检索层    改写 → 混合召回 → RRF → Rerank → ACL → 压缩    │
├─────────────────────────────────────────────────────┤
│ 索引层    PostgreSQL / MinIO / ES / Qdrant / Redis / Neo4j│
├─────────────────────────────────────────────────────┤
│ 解析层    MinerU / Docling / PaddleOCR / Unstructured  │
├─────────────────────────────────────────────────────┤
│ 接入层    上传 / Webhook / 站点爬取 / 业务API / IM同步  │
└─────────────────────────────────────────────────────┘
```

### 各层主流选型与推荐

#### 接入层
| 用途 | 主流方案 |
|---|---|
| 文件上传 | FastAPI / Spring Boot 上传接口，支持目录结构保留 |
| 网页采集 | Crawlee (JS动态站) / Scrapy |
| 业务系统对接 | Webhook + 增量事件 |
| IM 同步 | 飞书/钉钉开放平台 API（企业知识最大的真实来源） |
| 文档版本 | 内容 hash + 业务系统版本号双轨 |

#### 解析层 —— **本项目最大的成败关键**
| 方案 | 强项 | 弱项 |
|---|---|---|
| **MinerU 3.x** | 中文 PDF 表格/公式还原最强，输出 Markdown 带结构；3.1.0+ 原生支持 DOCX/PPTX/XLSX，许可证转 Apache 2.0 | 3.3 的 effort=medium 提速 35%~220% 但精度降 0.13 |
| **Docling (IBM)** | 版面分析干净，多格式统一 API | 中文表格偶尔掉结构 |
| **Unstructured** | 生态最全，chunking 插件丰富 | 商业版才有好效果，开源版一般 |
| **PyMuPDF** | 极快 | 只做文本抽取，结构全丢 |
| **PaddleOCR** | 中文扫描件/图片 OCR 最准 | 只管文字，不管版面语义 |
| **Apache Tika** | 元数据抽取全 | 复杂结构无能为力 |

**推荐组合**：`MinerU`（版式还原）→ `PaddleOCR`（扫描件兜底）→ `Docling`（兜底其他格式），三路输出统一转 Markdown，再交给切分层。
> 关键点：**务必保留表格为 Markdown 表格或 HTML 表格**，不要拍平成纯文本。财务/对比类表格拍平后检索效果直接归零。

#### 切分层
主流做法有三条路线：
1. **固定长度切分**（LangChain RecursiveCharacterTextSplitter）— 简单，但割裂语义
2. **语义分块**（按相似度断句）— 效果好，但慢
3. **结构感知 + 层级父子块**（推荐）

**推荐方案**：
- 父块 = 文档章节/标题下的完整段落（2000-4000 token），用于喂给 LLM，保证上下文完整
- 子块 = 父块内滑窗切出的小块（300-500 token），用于向量检索，保证召回精度
- 命中子块 → 回填父块 → 进 LLM。这是当前工业界公认最稳的 "Small-to-Big" 模式

元数据要带的字段：`doc_id / kb_id / 标题路径 / 页码 / 层级 / 章节 / 部门 / ACL主体 / 源URL / 内容hash / 版本号 / 生效时间`

#### 索引层
| 存储 | 主流选项 | 推荐 |
|---|---|---|
| 结构化业务数据 | PostgreSQL / MySQL | **PostgreSQL** |
| 原始文件 | MinIO / S3 / OSS | **MinIO**（私有化标配） |
| 全文+向量一体 | Elasticsearch 8.x / OpenSearch | **ES 8**（BM25 + HNSW 同源，过滤能力强） |
| 专用向量库 | Qdrant / Milvus / pgvector / Weaviate | **Qdrant**（过滤 + 性能 + 运维简单） |
| 缓存 | Redis | **Redis**（语义缓存、限流、会话） |
| 图数据库 | Neo4j / NebulaGraph / TuGraph | 可选，GraphRAG 才需要 |
| 消息队列 | Kafka / Redis Stream | **Redis Stream** 起步，规模上来换 Kafka |

**为什么 ES + Qdrant 双引擎而不是只用一个？**
ES 负责 BM25 关键词精确匹配（产品型号、工号、合同条款号这类"必须字面命中"的查询，BM25 完胜向量）；Qdrant 负责语义相似召回。两路结果用 **RRF（Reciprocal Rank Fusion）** 融合，而不是手工加权 —— RRF 无需调参、对两路分数尺度不敏感，是目前最稳的主流做法。

> 极简路线：PostgreSQL + pgvector + PG 全文检索，一个库搞定全部，适合 <50 万 chunk。规模再大再拆。

#### 检索层
| 能力 | 主流方案 |
|---|---|
| Query 改写/扩展 | Multi-Query（同义改写多路）、HyDE（先生成假设答案再检索）、Query 分解（复杂问题拆子问题） |
| 混合召回 | ES BM25 + Qdrant Dense |
| 融合 | **RRF**（推荐，无需调参）/ 归一化加权 |
| 重排 | **bge-reranker-v2-m3**（开源中文首选）/ Qwen3-Reranker / Cohere Rerank |
| 上下文压缩 | 上下文裁剪 / 抽取式压缩（LLMLingua 系） |
| 权限过滤 | **必须在检索阶段做 ACL pre-filter**，见第 3 节 |

**主流共识已从"纯向量 RAG"转向"混合检索 + Rerank"**。2023 年的朴素向量 RAG 在中文企业场景基本不可用，现在标准链路是：
```
用户问题 → 改写(多路) → BM25召回 ⊕ 向量召回 → RRF融合 → Rerank Top-K → ACL过滤 → 上下文组装 → LLM
```

#### 生成层
| 项 | 主流方案 |
|---|---|
| LLM | **DeepSeek-V4.1-Flash**（API 名 `deepseek-flash`）/ Qwen3 / Claude（国产合规优先） |
| 网关 | **LiteLLM**（统一协议 + 路由 + 成本统计 + 降级） |
| 提示词管理 | 模板化 + 版本化，放 DB 或 PromptHub |
| 引用溯源 | chunk_id 回写，答案内联 `[1][2]` + 原文高亮跳转 |
| 结构化输出 | JSON Schema / Function Calling（用于答案 + 引用 + 置信度一起返回） |

#### 应用层
| 项 | 主流方案 |
|---|---|
| 前端 | **React + TypeScript + Vite**（海外主流）/ Vue3 + Element Plus（国内主流），Tailwind + shadcn/ui |
| 后端 - AI 层 | **Python FastAPI**（RAG 生态在这） |
| 后端 - 业务集成层 | Java Spring Boot / Go（对接 OA/SSO/工单） |
| 编排 | **LangGraph**（有状态多轮 agent 编排，事实标准）/ Haystack / LlamaIndex |
| 权限 | **Casbin**（RBAC+ABAC，通用）/ OPA（策略即代码） |
| 认证 | Keycloak / 企业微信·飞书扫码 / OIDC |
| 观测 | **Langfuse**（RAG 专用可观测，主流）/ LangSmith / OpenTelemetry |
| 评估 | **RAGAS**（自动化指标主流）/ 人工标注集 / TruLens |
| 部署 | Docker Compose 起步 → **K8s + Helm + ArgoCD** |

## 2. 推荐基线栈（一句话版）

```
编排      LangGraph (Python 3.11+)
解析      MinerU 3.x（+ Office 原生兜底，无需 OCR）
切分      结构感知 + 父子块 (Small-to-Big)
索引      PostgreSQL + MinIO + Elasticsearch 8 + Qdrant + Redis
Embedding bge-m3（自托管，1024维/8192token，无 bge-m4 继任者）
Rerank    bge-reranker-v2-m3
LLM       LiteLLM 网关 → deepseek-flash (V4.1-Flash) / Qwen3
检索      BM25 ⊕ Dense → RRF → Rerank → ACL pre-filter
观测      Langfuse + Prometheus/Grafana
评估      RAGAS + 人工标注金标集
前端      React + TS + Vite + Tailwind + shadcn/ui
后端      FastAPI（AI）+ Spring Boot（业务集成）
部署      Docker Compose → K8s + Helm
```

## 3. 六个最容易踩的坑（工程真相）

### 坑 1：权限过滤做在检索之后 —— 直接等于数据泄露
如果先全库召回 Top-50，再在后置过滤里剔除无权文档，被剔除的片段**已经出现在 prompt 里**，大模型仍可能引用它。
✅ 正确做法：ACL 作为 **pre-filter 下推到 ES/Qdrant 的查询条件**（`filter: {"terms": {"acl_ids": [...]}}`），无权文档根本不进入候选集。
⚠️ 派生要求：用户→权限主体的映射要能在查询期高效求值，不能每次全表扫。

### 坑 2：只做向量检索，不做关键词检索
用户搜 "HT-2024-0873" 这种合同编号、"差旅报销标准" 这种制度名称，纯向量检索经常召不回或召错。
✅ 必须有 BM25 通道，两路 RRF 融合。

### 坑 3：文档解析质量不过关，后面全是无用功
90% 的"RAG 效果不好"，根因在解析层而不是检索层。扫描件、多栏排版、合并单元格表格、页眉页脚污染 —— 这些会让 chunk 变成垃圾。
✅ 建一个 **解析质量金标集**（人工标注 50-100 份典型文档），每次换解析器先跑一遍。
✅ 必须去页眉页脚、去目录页、保留表格结构。

### 坑 4：没有评估体系，全靠"我觉得还行"
✅ 上线前必须建两套：
- **检索评估**：金标 query 集 → Recall@5 / MRR / nDCG（先保证"召得回"）
- **生成评估**：Faithfulness（答案是否有据）、Answer Relevance、Context Precision（再保证"答得好"）
✅ RAGAS 自动跑 + 每周抽样人工评审。**没有评估集就没有迭代能力**，这是团队能不能持续改进的分水岭。

### 坑 5：忽略增量索引与数据新鲜度
企业知识库一半以上的价值来自"刚发的文件当天能被问到"。全量重建索引不可接受。
✅ 方案：内容 hash 变更检测 + 消息队列异步增量管线 + 软删除（旧 chunk 标记失效而非物理删）+ 定期全量校准。
✅ 源系统推送 webhook 优于定时轮询。

### 坑 6：跳级 —— V2 没扎实就上 GraphRAG
用复杂度掩盖基础问题是最常见的路径错误。GraphRAG 成本高（要额外建图、跑社区摘要），只解决特定类型的关系型问题。
✅ 严格按 V1 → V2 → V3 → V4 → V5 → V6 逐级验证，每一级的核心指标达标再进下一步。

## 4. 演进路线

| 阶段 | 能力 | 关键动作 |
|---|---|---|
| **V1 朴素 RAG** | 能问能答有引用 | 单路向量 + Top-K + 引用溯源。先跑通端到端 |
| **V2 混合检索** | 召回率显著提升 | BM25 + Dense + RRF + Rerank；解析换 MinerU |
| **V3 生产化** | 能上生产 | ACL pre-filter、增量索引、Langfuse 观测、RAGAS 评估集 |
| **V4 上下文工程** | 回答更准 | Query 改写/分解/HyDE、父子块、上下文压缩 |
| **V5 图谱增强** | 关系型问题 | Neo4j/NebulaGraph + GraphRAG（成本高，只解决特定问题类型） |
| **V6 Agent 化** | 多步复杂任务 | LangGraph 多 agent、工具调用、任务型工作流 |

⚠️ **不要跳级**。V2 没做扎实就上 GraphRAG，是典型的"用复杂度掩盖基础问题"。

## 5. 成本估算（1000 人企业 / 10 万份文档参考量级）

| 项 | 估算 |
|---|---|
| 解析 | 一次性，约 ¥0.1-0.5/页（自托管 GPU 约 ¥2-5k 一次性） |
| 存储 | 100 万 chunk × 1024维 × 4B ≈ 4GB 向量；ES+Qdrant+对象存储含原文 ≈ 60-100GB |
| Embedding | 1 亿 token 量级，自托管 bge-m3 ≈ 数千元 GPU 一次性 |
| 在线推理 | 单次问答：检索 ~100ms + rerank ~50ms + LLM 首字 ~1s → 端到端 2-4s |
| 月度 LLM 成本 | 1 万人 × 20 次/天 × 30 天 × 8k token ≈ 4.8 亿 token/月 → 按 ¥2/百万 token 估算约 ¥1 万/月量级 |
| 成本优化 | 语义缓存(Redis) + 分级路由(简单问题走小模型) + 上下文裁剪 + Prompt 缓存，通常可降 40-60% |

## 6. 落地路线图

```
第 1-2 周   技术选型验证：20 份真实文档跑通解析→检索→生成，看引用是否靠谱
            产出：解析质量金标集 v1 + 端到端 demo
第 3-4 周   MVP：上传 + 解析 + 索引 + 混合检索 + 对话 + 引用溯源
            产出：可用系统 + RAGAS 评估基线报告
第 5-6 周   生产化：权限模型（Casbin + ACL pre-filter）+ 增量索引 + Langfuse
            产出：权限矩阵通过安全评审
第 7-8 周   灰度上线：埋点、监控、评估周报、badcase 闭环流程
第 9-12 周  优化：Query 改写、父子块、上下文压缩；评估集扩容
第 3 季度   进阶：图谱增强 / Agent 工作流 / 多租户
```

**第一个真正该做的事**：拉 20 份最典型的真实文档（1 份扫描件 PDF、2 份带表格的 PDF、3 份 Word、若干网页/飞书导出），跑通 MinerU 解析，人工看 chunk 质量。**这一步的结果，会决定后面 80% 的架构决策。**

## 7. 待确认的问题

1. **部署形态**：私有化内网 / 公有云 SaaS / 混合？→ 决定模型自托管比例、是否要 air-gap 方案
2. **文档类型分布**：扫描件占比多少？表格多不多？→ 决定解析层投入权重
3. **权限模型复杂度**：是否需要部门级 + 密级（公开/内部/秘密）双重控制？
4. **团队技术栈**：Java 为主还是 Python 为主？→ 决定 AI 层与业务层的切分方式
5. **规模预期**：员工数、文档量、日问答量？→ 决定 ES+Qdrant 双引擎 vs 单库方案
